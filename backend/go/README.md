# Backend services

Go runs three independently configured APIs from the same codebase: `SERVICE_ROLE=resident` on port 8080, `SERVICE_ROLE=management` on port 8081, and `SERVICE_ROLE=admin` on port 8082. Each process exposes only its route group, checks a distinct frontend origin, and uses a separate staff session cookie. The resident API handles resident identity, property addresses, complaints, and payments; management handles resident service activity and operations; admin handles staff accounts, devices, settings, and audit records. The processes currently use one PostgreSQL database so service activity is available to authorized management routes. Python owns only the calibrated sensor distance validation and fill calculation and has no database access. The processor binds to loopback by default; set `PROCESSOR_BIND_HOST` to a private interface address when it must accept requests from a separate Go host. Do not expose this unauthenticated calculation service publicly.

## Local prerequisites

- Go 1.24 or newer
- Python 3.11 or newer (standard library only)
- PostgreSQL 15 or newer

Create a database and apply migrations `001_iot.sql` through `014_monthly_service_invoices.sql` in numeric order from `db/migrations`. Migration 011 adds a separate property application review state while preserving existing property/bin statuses and payment history. Migration 012 adds case-insensitive unit-code uniqueness; it stops without changing unit records if legacy duplicates need reconciliation. Migration 013 links bins to resident accounts where existing memberships identify one account and records each scanned evacuation; ambiguous legacy bin assignments remain unresolved until management confirms the account. Each API process needs `DATABASE_URL`, `SESSION_SECRET` (at least 32 characters), `SERVICE_ROLE`, and its own `SERVICE_ORIGIN`. The Go service does not load `.env` files. Run `go run ./backend/go` in three processes with `SERVICE_ROLE` set to `resident`, `management`, and `admin`; `PORT` can override each service's default port.

Create the first administrator once, after applying migrations. Set `BOOTSTRAP_ADMIN_PASSWORD` and run `go run ./backend/go bootstrap-admin "Full Name" "admin@example.test" "+234..."`. There is no default password, and bootstrap refuses to run when an active system administrator exists. Enable `DEV_RESET_LINKS=true` only in local development to show a one-time recovery token in the UI; real email delivery is not configured.

Devices are provisioned in the system administration workspace. Their raw token is shown once, and only its SHA-256 hash is stored. Requests require both `X-Device-ID` and `X-Device-Token`; the body must identify the same device. Simulator state comes from the registered device record and cannot be asserted by the incoming reading. For a two-sensor skip, register both sensor devices against the same container. Operations uses each enabled sensor's latest fresh fill estimate and reports the highest fill estimate; the displayed signal time is the time of that selected reading. No physical sensor is currently connected.

Resident accounts can own multiple labeled locations such as a home and shop. New complaints and payments must reference a location belonging to the signed-in resident, and the management payment and complaint endpoints include the saved service address. Payment records use integer kobo and are scoped to the resident who created them. Each service area has one 60 L base fee. A delivered bin assigned to a resident is priced in proportion to its capacity (for example, 120 L costs twice the base); residents with multiple assigned bins pay the sum of those bin prices, with no additional area fee. Management records the printed tracking ID, unit and resident account when handing over a bin. At collection, staff scan or enter the same tracking ID in Operations to record a timestamped evacuation event; the resident property view displays the latest recorded evacuation and refreshes while open. An account email can be confirmed during handover or used to reconcile an older bin that has no unambiguous account link. Missing base fees or unresolved bin assignments block payment initialization rather than silently omitting a bin. The simulation flow is available only outside production when `PAYMENT_MODE=simulation` and an administrator has configured the applicable area fee. It creates a demonstration receipt and explicitly records that no funds moved. Monthly service invoices are prepared by the resident API for each address with a configured billable fee, using the delivered-bin fee calculation. They are due on the 7th, unpaid invoices remain outstanding, and the amount and bin-fee breakdown are saved as a monthly snapshot. The scheduler prepares the next month after the 7th so a mid-month deployment does not create an immediately overdue invoice. Migration 014 creates invoice storage. A real payment provider is not connected; invoices can be shown as due but cannot yet be paid online, and production payment initiation remains disabled.

## Connecting separately hosted frontends

The Vite frontend calls the resident, management, and admin APIs through `VITE_RESIDENT_API_URL`, `VITE_MANAGEMENT_API_URL`, and `VITE_ADMIN_API_URL`. Set those build-time variables to the deployed HTTPS API base URLs, including `/api/v1`. If a dashboard is served at the root of its own site, set `VITE_APP_ROLE=management` or `VITE_APP_ROLE=admin` for that build; the `/management.html` and `/admin.html` pages select their matching APIs automatically. In production, a missing API URL produces a clear request error rather than silently trying to contact localhost.

Set each API process's `SERVICE_ORIGIN` to the exact browser origin serving its frontend (scheme, hostname, and port, with no path). For example, if the resident site is `https://www.example.ng`, its API process must allow that origin; configure the management and admin origins independently. The APIs use credentialed CORS, and browser requests include cookies. Keep each frontend and its API under the same site (for example, subdomains of `example.ng`) so the `SameSite=Lax` session cookies work in browsers. Use HTTPS in production.

The management and admin APIs must also be reachable only through staff VPN/private networking or an identity-aware access gateway. CORS controls which browser origins can read responses; it does not block direct requests to a public API. Keep PostgreSQL and the Python processor private as well.

## Using Neon

The Go APIs use the existing `pgxpool` driver and read `DATABASE_URL` from the process environment. Use Neon's pooled `DATABASE_URL` for API traffic; use `DATABASE_URL_UNPOOLED` for schema migrations. Never expose either value through a `VITE_` variable or browser code.

After linking the Neon project and pulling its variables into the repository-root `.env.local`, start the local frontends and APIs with `powershell -ExecutionPolicy Bypass -File scripts/start-local.ps1 -UseNeon`. This mode uses the pooled URL, does not rerun migrations, and disables payment simulation and development reset links. The normal `scripts/start-local.ps1` command continues to use local PostgreSQL and its existing migration flow.

For Render, set the pooled `DATABASE_URL` as a secret environment variable on each Go API service. Keep each service's `SERVICE_ROLE`, `SESSION_SECRET`, and `SERVICE_ORIGIN` configured independently. Set the frontend's `VITE_RESIDENT_API_URL`, `VITE_MANAGEMENT_API_URL`, and `VITE_ADMIN_API_URL` to the corresponding deployed API URLs; these are API URLs, not database connection strings.

## IoT endpoint

`POST /api/v1/iot/readings` accepts JSON `{ "device_id": "...", "measured_at": "RFC3339 timestamp", "distance_cm": 42.5 }` plus the two device headers. Go reads the registered skip's dimensions and thresholds, delegates fill calculation to Python, persists only valid readings, and creates an operational notification when the status crosses into warning or critical. Duplicate device/timestamp pairs return a conflict. `GET /healthz` checks PostgreSQL connectivity.

Go/Python unit tests do not need a database. Account and workflow routes require PostgreSQL migrations to be applied.
